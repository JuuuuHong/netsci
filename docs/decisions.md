## 2026-09-17 2차 코드 리뷰 반영
- 선택지: 중간 등급만 / 낮음 등급까지 전부
- 선택: 전부 (확신 낮은 참고 사항 5건은 제외)
- 이유와 내용:
  - **한도 소진 에러에서도 부분 결과 작성**: 요청 자체가 `BudgetExhausted` 로 실패하면 지금까지 받은 페이지로 `works.jsonl` 을 쓰고 `stopped_by_budget = true`. 에러로 끝내면 `--limit` 을 줄인 재실행도 `query.json` 불일치로 막혀 다음 날까지 분석을 못 한다. (이 불일치 사유는 아래 "캐시 일치 판정에서 `limit` 제외" 로 해소됐다. 부분 결과 작성은 유지한다.)
  - **한도 소진 판정은 재시도 대상 응답(429/5xx)에서만**: 400 같은 요청 오류는 원래 에러 본문을 보여 준다.
  - **`query.json` 없이 캐시 페이지만 있으면 에러(`OrphanCache`)**: 어느 질의의 캐시인지 모르는데 새 질의로 덮으면 캐시가 섞인다. 그래서 테스트도 캐시 페이지를 둘 때 `query.json` 을 함께 둔다.
  - **`results: null` 허용, 깨진 캐시 파일은 지우라고 안내**: 모델(`WorksPage`)의 관대한 파싱과 맞춘다.
  - **`works.jsonl` 도 임시 파일 + rename**: 쓰다 끊기면 잘린 코퍼스가 남는다.
  - **`--min-score` 는 0~1 의 유한한 수만**: `NaN` 은 모든 비교가 거짓이라 빈 표를 조용히 낸다.
  - **Broken pipe 는 정상 종료**: `netsci ... | head` 에서 패닉(종료 코드 101)하지 않게 한다.
  - **render 는 셀 수를 헤더 수에 맞춘다**: 계약을 어긴 수동 `Report` 구현에서도 표와 CSV 가 같은 모양이 된다.
  - **derive**: `Option` 판별 시 `macro_rules!` 그룹·괄호 타입을 벗긴다. `precision` 을 정수·`bool`·`char`·`String`·`str`(및 그 `Option`)에 쓰면 컴파일 에러(문자열은 잘리고 정수는 무시되는 함정). `skip = …` 에는 "값을 받지 않는다" 에러, `precision` 은 `u16` 범위 밖이면 속성 위치에 에러. → 2026-09-17 대체: `Option` 판별과 `precision` 타입 이름 목록은 아래 "derive 의 타입 판정을 트레이트로" 에서 트레이트 구현 판정으로 바꿨다.
  - **테스트 보강**: PageRank 정확값·고정점 테스트, 로컬 TCP 서버로 `HttpClient` 재시도·한도·요청 간격 테스트(`tokio` 기능을 늘리지 않으려고 표준 라이브러리 `TcpListener` 사용, 요청 간격 기대값은 구현 상수 대신 명세 값 100ms 를 직접 적음). trybuild 는 명세의 3건에 새 에러 3건을 더했다.
  - **Linux Docker 권한**: 이미지는 명세대로 비루트로 두고, README 에 Linux 용 `--user "$(id -u):$(id -g)"` 명령을 따로 적었다 (명세의 사용 예는 그대로 유지).
    Docker Desktop(macOS) 바인드 마운트는 소유권을 바꿔 보여 주므로, Docker VM 의 Linux 파일시스템(named volume)에 uid 1000·755 디렉터리를 만들어 확인했다: 기본 실행(uid 10001)은 `Permission denied`, `--user 1000:1000` 은 성공, root 소유 디렉터리는 `--user` 로도 실패(그래서 `mkdir -p data` 를 먼저 안내).

  - `impl<T: Display> Cell for T` 포괄 구현은 두지 않았다. `Option<T>` 구현과 겹친다고 보고 거부된다(E0119, 상위 크레이트인 std 가 나중에 `Option` 에 `Display` 를 구현할 수 있다는 규칙). 그래서 표준 타입마다 구현하고, 사용자 정의 `Display` 타입에는 `#[report(display)]`(`ToString::to_string` 호출, `precision` 과 함께 쓰면 에러)를 둔다. `Option<사용자 타입>` 은 `display` 로 `None` 을 처리할 수 없으므로 그 타입에 `Cell` 을 구현한다
  - 호출을 `<T as Trait>::method` 로 만든 것은 에러 위치 때문이다. `Cell::cell(&self.field)` 처럼 `Self` 를 추론에 맡기면 E0277 의 주 위치가 `#[derive(Report)]` 였고, 한정 경로로 바꾸자 사용자가 쓴 필드 타입(`name: String` 의 `String`)을 가리켰다. 트레이트에 `#[diagnostic::on_unimplemented]` 로 `#[report(display)]`·부동소수 전용이라는 안내를 붙였다. 괄호 타입 `(T)` 은 한정 경로에 넣으면 사용자 span 에 `unused_parens` 경고가 나서 괄호만 벗긴다
  - 트레이트는 숨기지 않고 공개한다. 사용자가 자기 타입에 `Cell` 을 구현해야 `Option` 안에 넣을 수 있기 때문이다. 제네릭 구조체에는 명세(§6.3)대로 바운드를 더하지 않으므로 `T: Cell` 을 사용자가 적는다
- 결과: 기존 행 타입의 출력 문자열은 바뀌지 않았다(`f64` 의 `format!("{:.N}")` 와 `Display` 를 그대로 쓴다. 실제 코퍼스 두 개로 모든 명령·형식 48개 출력을 변경 전후 바이트 비교). trybuild: `precision_on_string` 은 별칭 뒤 `Option<u32>`·`Cow<str>` 를 더해 트레이트 에러로, `non_cell_field`(사용자 정의 타입·그 `Option`)·`display_with_precision` 추가(8건)

## 2026-09-17 매개 개념 B 제안(`gaps --bridges K`) — 점수 정의 (결과를 보기 전에 기록)
- 선택지: `min(weight(A,B), weight(B,C))` 가중치(공존 수) 순 / `min(lift(A,B), lift(B,C))` 순 / 두 간선 lift 의 곱·조화평균
- 선택: 두 간선 lift 의 최솟값 내림차순. 후보 B 는 A·C 가 아니고 `works(B) >= min_works` 이며, 두 간선 모두 공존 3편 이상이고 lift 가 1 을 넘는 것(`observed × N > works × works`)만. 동점이면 두 간선 공존 수의 최솟값 내림차순, 이름 오름차순, 개념 번호 오름차순. 기본 `K = 0` 은 지금과 같은 행 타입·출력이고, `K > 0` 이면 `bridges` 열이 붙는다. 셀은 `B (A와 공존|C와 공존)` 를 `; ` 로 잇는다
- 이유:
  - **허브 편향**: 공존 수의 최솟값은 코퍼스 대부분에 붙는 레이블(리튬의 `Electrolyte`·배터리 토픽, RAG 의 `Language model`·`Topic Modeling`)이 거의 모든 쌍에서 1위가 된다. 그런 B 는 A·C 에 대해 아무것도 말하지 않는다. lift 는 B 의 빈도로 나누므로 "A 논문에서 B 가 기대보다 잦고 C 논문에서도 잦은" 레이블을 올린다. 최솟값을 쓰는 이유는 한쪽 간선만 강한 B(A 와만 얽힌 하위 개념)를 매개로 보지 않기 위해서다 (약한 고리 기준)
  - **lift > 1 조건**: 독립보다 덜 함께 나오는 B 는 A 와 C 를 잇는다고 볼 근거가 없다. 조건을 만족하는 B 가 없으면 빈 칸이다
  - **공존 3편 하한**: lift 는 작은 수에서 크게 흔들린다(공존 1편이 lift 수십이 될 수 있다). `MIN_EXPECTED = 3` 과 같은 크기로 정했고 결과를 보고 바꾸지 않는다
  - 비교는 N 이 공통이라 `observed / (works_a × works_b)` 를 정수 교차곱으로 해 동점을 정확히 판정한다 (gaps 와 같은 방식)
- 한계: 동시출현 lift 는 "함께 태깅됐다" 일 뿐 A→B→C 의 기전이 아니다. B 는 가설 후보를 읽을 실마리이고 README 에는 결과를 보고 고르지 않도록 미리 정한 쌍만 싣는다: 리튬 `gaps --taxonomy concepts --top 3 --bridges 3`, RAG `gaps --top 3 --bridges 3`(topics, README 가 분야별로 쓸 만하다고 본 분류)

## 2026-09-17 시간 분할 검증(`backtest`) 설계와 분할 연도 — 사전 등록 (결과를 보기 전에 기록)
- 선택지: 무작위 분할 / 연도 기준 hold-out
- 선택: 연도 기준. `backtest --split-year Y [--top N] [--min-works W] [--taxonomy T] [--min-level L] [--min-score S] [--summary]`
- 설계:
  - train = 연도 ≤ Y, test = 연도 > Y. 연도가 없는 작품은 둘 다에서 뺀다. 레이블 필터·`min_works`·`expected`·후보 쌍은 **train 만으로** 계산한다(`gaps` 와 같은 규칙, `expected >= 3`). test 는 같은 필터로 따로 그래프를 만들고 레이블 id 로 짝짓는다
  - 쌍마다 `test_observed`(test 에서 A·C 가 함께 붙은 논문 수), `test_expected = test_works_a × test_works_b / N_test`, `test_lift = test_observed / test_expected`. 한쪽 레이블이 test 에 없으면 `test_expected = 0`, `test_lift` 는 빈 칸
  - 기본 출력: train 공존 0 인 쌍 중 `gaps` 순위 상위 N 개와 train·test 통계. `--summary`: 집단별 요약 — 상위 N 공백 후보 / train lift = 0 전체 / (0, 0.5) / [0.5, 1) / [1, 2) / ≥ 2 / 전체 후보(기준선). 열은 쌍 수, test 공존 1편 이상 비율(hit rate), test 기대값 3 이상인 "판정 가능" 쌍 수와 그 안의 hit rate, 판정 가능 쌍의 `test_lift` 중앙값, `test_expected` 중앙값
  - train lift 구간은 부동소수 대신 정수 비교(`observed × N` 과 `works_a × works_b` 의 배수)로 나눈다
  - 한 표에 행 타입이 둘이면 CSV·JSON 이 깨지므로 `--summary` 플래그로 나눈다. train·test 편수는 stderr 에 한 줄로 알린다
- 해석 주의 (README 에도 쓴다): test 공존은 "가설이 맞았다" 가 아니라 "나중에 함께 태깅됐다" 이다. 흔한 레이블끼리는 test 기대값이 커서 공존이 쉽게 생기므로 hit rate 는 집단마다 기준선(전체 후보)과 test 기대값을 함께 봐야 한다
- 분할 연도 규칙: 연도별 누적 비율이 처음 50% 이상이 되는 연도 Y. 그 연도가 마지막 연도라 test 가 비면 바로 앞 연도. 위 규칙과 `works.jsonl` 연도 분포로 정한 값:
  - `data/li-anode-phrase`(인용 > 20, 4,438편): 누적 2021년 50.6% → **Y = 2021**
  - `data/li-anode-phrase-all`(인용 필터 없음, 9,934편): 2022년 57.8% → **Y = 2022**
  - `data/rag-phrase`(964편): 2024년에야 100% → 앞 연도 **Y = 2023** (2023년까지 34.3%)
  - `data/rag-phrase-all`(10,681편): 2024년에야 100% → **Y = 2023** (2023년까지 19.2%)
- 실행 목록 (모두 보고한다): 네 코퍼스 × `--taxonomy topics`·`concepts` × (`--top 20` 표, `--top 20 --summary`), 다른 값은 기본(`--min-works 15`, 기본 필터). 문턱값을 바꾼 추가 실행은 하지 않는다
- 주 분석은 **인용 필터 없는 코퍼스**로 정한다. `cited_by_count > 20` 은 2026년 시점의 피인용으로 고른 것이라, 필터 코퍼스의 train 논문은 분할 뒤에 쌓인 인용(미래 정보)으로 선택된다. 필터 코퍼스 결과는 비교용으로 함께 싣는다

## 2026-09-21 AUROC 의 동점 처리와 precision@k 의 경계 처리
- 선택지: 동점을 임의 순서로 가른다 / midrank(양쪽 0.5) / 동점을 아예 뺀다

- `gap_precision_at_k` 는 점수와 레이블을 함께 뒤집어 같은 함수로 잰다. 부호 반전은 f64 에서 오차가 없다.

  - 이웃 기반 점수(`common_neighbors` 0.607~0.901, `adamic_adar` 0.622~0.910, `jaccard` 0.493~0.847)는 `above_chance` 기준 8개 실행에서 모두 lift 아래였지만, `co_tagged` 기준의 `rag-phrase-all` concepts 한 실행에서는 셋 다 lift(0.741)를 앞섰다(0.784·0.798·0.765). **초안에 "어느 기준으로도 넘은 실행은 없었다" 고 잘못 적었다가 검증에서 바로잡았다 — 그 반례는 README 요약 표에 이미 인쇄돼 있었다**.

  사전 등록은 "**수치를 싣되** 읽지 않는다고 표시한다" 였는데 초안은 표에서 통째로 뺀 뒤 "수치는 남겼다" 고 적었다 — **사전 등록 위반이자 사실과 다른 서술이었고, 검증에서 별도 표로 실어 바로잡았다.**

  - 실측 수치: `topics · above_chance`(12쌍, 기준선 0.500) lift 0.875 · cooccur 0.889 · pref_att 0.764 · common_nb 0.667 · adamic 0.694 · jaccard 0.597 · random 0.444
  - 네 실행 모두 `k` 가 쌍 수로 줄어(12·1) `precision_at_k` 가 모든 점수에서 `base_rate` 와 같다(k = 쌍 수이면 상위 k 개가 전체다). 점수 간 변별이 남은 열은 `topics` 의 `auroc` 뿐이다
  - `concepts` 는 판정 가능 쌍 1쌍이 양성이라 음성이 0 이다. `base_rate` 1.000 은 "기준선 100%" 가 아니라 표본이 1쌍이라는 뜻이므로 표에 양성·음성을 나눠 적었다
- 이 평가는 "가설이 맞았다" 를 재지 않는다. 높은 AUROC 는 점수가 재현된다는 뜻이지 레이블이 옳다는 뜻이 아니다 — 리튬 topics 의 토픽 자리 포화 같은 배정 방식 산물도 시간에 따라 유지되어 높은 AUROC 를 받는다

## 2026-09-21 AUROC 0.5 를 귀무값으로 읽은 것이 틀렸다 — 순열 귀무기준 도입

- **양성 기준과 점수 사이의 순환**: `above_chance`(test 의 `observed/expected >= 1`)는 train 의 lift 를 test 기간에 그대로 적용한 기준이고, `co_tagged` 는 독립 가정 아래 최적 예측자가 `works_a × works_b`(= `preferential_attachment`)인 기준이다. 두 기준이 각각 자기와 같은 정규화를 쓰는 점수를 보상한다. 순환을 없애는 제3의 기준은 찾지 못해 **두 기준을 모두 보고하는 것으로 갈음한다**
- **lift 의 변별력 상당 부분이 "train 공존 0인가" 이진 구분**이다. 평가 쌍의 절반 가까이가 `lift = 0` 단일 동점 블록이라 그 안에서는 순서를 주지 못한다
- **불확실성 구간 없음**: `z` 는 귀무 쪽 흔들림만 보여 주고 관측 AUROC 의 오차나 점수 간 차이의 유의성은 재지 않았다. 쌍이 독립이 아니라(개념 하나가 수백 쌍에 참여) 소박한 이항 구간도 너무 좁다. 개념 단위 부트스트랩·DeLong 짝지은 검정은 하지 않았다. 그래서 **"16/16" 은 부호를 센 것일 뿐 유의성 주장이 아니다**라고 명시했다
- **판정 가능 필터의 방향성**: `base-editing-all` concepts 는 후보 4,043쌍 중 640쌍(84% 제거), `rag-phrase-all` 은 951쌍 중 158쌍만 남는다. 필터는 필요하지만 lift·공존 수 쪽 AUROC 를 올리고 이웃 기반 점수를 내리며 분할 연도를 뒤로 밀수록 커진다
- **이웃 정의에 문턱이 없다**: 공존 1편이면 간선이라 `base-editing-all` 쌍당 공통 이웃이 concepts 82.1개·topics 12.6개로 포화된다. "이웃 기반 점수가 졌다" 의 일부는 연관 강도가 아니라 이 설계 선택의 결과다
- **AUROC 로 꼬리를 주장하지 않는다**: 전역 평균이라 "공백 후보 쪽" 을 주장할 수 없다. 그 역할은 `gap_precision_at_k` 뿐이다. 모듈 주석과 SPEC §5.8 의 해당 문장을 지웠다

**코드로 고친 것**

- `Neighborhood::common` 의 `l != a && l != b` 제거 — 간선 키가 `a < b` 라 자기 간선이 없어 `a ∉ N(a)` 이고, 따라서 도달 불가다(실측 170만 건 중 0건 발동). 실제로 빼야 하는 곳은 `a`–`b` 가 이어지면 `a ∈ N(b)` 가 되는 `union_size` 쪽이라 거기만 남겼다. `adamic_adar` 의 `deg(z) > 1` 도 같은 이유로 뺐다

## 2026-09-21 `adamic_adar` 의 합산 순서를 항 값으로 고정
- **순열 순서 불변 테스트가 실제 결정성 버그를 잡았다.** 같은 코퍼스를 뒤집어 읽었을 때 `adamic_adar` 의 귀무 AUROC 가 0.6 대 0.5 로 갈렸다(관측 AUROC 는 양쪽 1.0 으로 같아 눈에 띄지 않았다)
- 원인: `Neighborhood::common` 은 이웃을 **개념 번호** 순으로 내는데 그 번호는 코퍼스를 읽는 순서에 따라 달라진다. 부동소수 덧셈은 결합법칙이 성립하지 않으므로 같은 항을 다른 순서로 더하면 마지막 자리가 갈리고, 동점이어야 할 쌍이 갈라져 AUROC 가 미세하게 달라진다
- 선택지: 이웃을 id 순으로 정렬한다 / 항 값으로 정렬해 더한다 / 그냥 둔다
- 선택: **항 값으로 정렬한 뒤 더한다**. 인접 목록은 합쳐 훑기(merge) 때문에 개념 번호 순이어야 하므로 그쪽은 건드릴 수 없다. 항의 다중집합은 순서와 무관하게 같으므로 값으로 정렬하면 순서가 정해지고, 작은 항부터 더해 수치 안정성도 조금 낫다
- 점수 7개 중 부동소수를 누적하는 것은 `adamic_adar` 하나뿐이다(나머지는 정수 개수이거나 쌍 필드에서 바로 온다). 실제 코퍼스 결과 수치는 바뀌지 않았다(README 표와 바이트 단위 동일)
- **교훈**: 이 저장소는 해시맵 순회 순서·동점 정렬까지 통제해 왔는데, 부동소수 **합산 순서**라는 경로가 남아 있었다. 순열이라는 난수 경로를 들이면서 비로소 드러났다

## 2026-09-21 `union_size` 의 쌍 자신 제외는 남긴다 — 도달 가능하고, 테스트로 고정했다
- `Neighborhood::common` 의 `z != a && z != b` 는 도달 불가라 뺐지만(`a ∉ N(a)`), `union_size` 의 같은 모양 필터는 **살아 있다** — a–b 가 이어져 있으면 `b ∈ N(a)` 가 되고, 후보 쌍은 대부분 train 공존이 1 이상이라 상시 발생한다. 두 자리는 대칭이 아니다
- 리뷰에서 이 필터를 지우면 실제 코퍼스의 Jaccard 값이 움직이는데(0.182 → 0.181) **당시 테스트가 전부 통과**했다. 세 번째 소수 자리만 조용히 바뀌는 종류라 더 위험하다
- m3 에서 넣은 이웃 점수 픽스처가 이 돌연변이를 잡는다(Jaccard AUROC 0.300 → 0.600). 돌연변이를 실제로 주입해 실패를 확인했고, 주석에 그 사실을 적었다
- SPEC §5.8 의 "공통 이웃과 합집합에서 쌍 자신을 뺀다" 는 합집합 쪽만 참이므로 고쳤다

## 2026-09-21 짝지은 순열 검정 도입 — "16/16" 도 과했다 (세 번째 정정)
- **지적**: `excess` 는 점수마다 **따로** 잰 귀무를 빼는데, "lift > X" 는 두 점수의 *차이* 에 대한 주장이다. 차이의 불확실성을 담지 않으므로 부호를 세는 것은 잡음을 세는 것일 수 있다

- **구현**: §5.9 의 순열을 그대로 쓰되, 순열마다 점수 7개의 AUROC 를 **한 행**(`[f64; 7]`)으로 모은다. AUROC 정의 여부는 레이블에만 달려 7개가 동시에 정의되므로 짝짓기가 구조적으로 보장된다. `--reference`(기본 `lift`)와 `delta`·`delta_null`·`p_value` 열을 더했다. 추가 비용은 없다(순열을 이미 공유한다)

## 2026-09-21 계층화 AUROC 추가 — 빈도 점수의 겉보기 실력은 주변크기 교란이었다
- **문제(B의 절반)**: `co_tagged`·`above_chance` 두 양성 기준이 모두 주변빈도와 상관되므로, 전체에서 한 번 잰 AUROC 에는 "그 쌍이 얼마나 흔한가" 가 섞인다. 특히 `co_tagged` 는 독립 가정 아래 최적 예측자가 `works_a × works_b` 라 빈도 점수를 구조적으로 보상한다
- 선택지: 제3의 양성 기준을 만든다 / 계층화 AUROC 를 잰다 / 한계로만 적는다
- **제3의 기준으로는 못 푼다**: test 기간이 주는 양은 `test_observed`·`test_works_a`·`test_works_b`·`N_test` 넷뿐이고 모든 레이블은 이들의 함수다. 축은 하나(원시 공존량 ↔ 완전 정규화)이고 두 기준이 이미 양 끝이라 제3은 탈출이 아니라 내삽이다. "test 공존이 train 대비 증가했는가" 류는 레이블이 점수 자신의 함수가 되어 **지금 없는 진짜 순환**을 만든다 — 레이블은 test 만 봐야 한다
- **선택: 계층화 AUROC**(`test_expected` 십분위 안에서 재고 쌍 수로 가중평균). 순열 없이 정렬 한 번이라 비용이 거의 없다
- **결과 (읽는 16회, 계층화 − 원래의 평균)**: `preferential_attachment` **−0.112**(최대 −0.285), `common_neighbors` −0.050, `adamic_adar` −0.043, `jaccard` −0.007, `cooccurrence` −0.005, `lift` **−0.003**, `random` +0.033
  - `li-anode-phrase-all` concepts `co_tagged` 에서 PA 0.790 → 0.637, `li-anode-phrase` topics `co_tagged` 에서 0.755 → 0.470
  - **빈도 점수의 겉보기 실력은 대부분 주변크기 교란이었고, lift 는 그 교란에 거의 기대지 않는다**
- **진단용으로만 쓴다.** 계층화 값에는 짝지은 검정을 붙이지 않았으므로 우열 주장에 쓰지 않는다. 구현 검증: 독립 구현과 수치가 일치했다(topics lift 0.868·cooccur 0.866·PA 0.536·common_nb 0.809, concepts PA 0.649)
- 쌍이 계층 수보다 적으면 값이 없다. 계층을 억지로 합치지 않는 것은 합치는 규칙이 결과를 좌우하는데 그 규칙을 정당화할 근거가 없기 때문이다

## 2026-09-21 순열이 고친 것은 기준선이지 순환이 아니다 — 두 한계를 분리해 적는다
- 초안 수정 중에 "순열 귀무기준이 순환 문제도 해결한다" 로 읽힐 서술을 할 뻔했다. **틀리다.**
- 귀무 아래에는 연관이 아예 없어 lift 의 귀무값이 0.5 근처로 나온다. 양성 기준이 lift 와 같은 정규화를 쓴다는 구조적 이점은 **실제 연관이 있을 때만** 드러나므로, 순열은 그 이점을 재지도 지우지도 않는다
- 순열이 고친 것은 **기준선 오류**(AUROC 0.5 를 귀무로 읽은 것)뿐이다. 순환은 별개이고 계층화가 그 절반(빈도 보상)을 줄일 뿐, `above_chance` 가 lift 의 정규화를 그대로 쓴다는 사실은 남는다. README 한계에 두 항목으로 나눠 적었다
- 다중비교 보정은 하지 않는다. 기준 하나 대 6개 비교를 한 번에 읽을 때를 위해 Bonferroni(0.05/6 = 0.0083) 수치를 표에 함께 실었다. 순열 200회의 p 하한이 0.005 라 그 기준에 닿는다
- `co_tagged` 의 기준선은 test 창 크기에 좌우되므로(같은 리튬 코퍼스에서 분할 2020 이면 0.552, 2023 이면 0.256~0.510) **분할 연도가 다른 실행 사이에 `co_tagged` 수치를 비교하면 안 된다**고 한계에 적었다

## 2026-09-21 귀무 AUROC 범위를 순열 200회 결과로 바로잡음
- README(2곳)·SPEC §5.9·`evaluate.rs` 모듈 주석의 "실측 0.37~0.93" 은 **순열 20회** 때 수치였다. 기본값을 200회로 올린 뒤 다시 적지 않아 남아 있었다
- 순열 200회 기준: **순열을 모두 쓴 실행에서 0.41~0.81**. 쓸 수 있는 순열이 적은 소표본 실행까지 넣으면 0.22~0.95 로 넓어지는데, 양끝이 모두 `li-anode-phrase · topics · co_tagged`(쓸 수 있는 순열 88회)에서 나왔다. 그 실행의 `random` 귀무값이 0.223 으로 0.5 에서 크게 벗어난 것 자체가 생존 편향의 흔적이라, 대표 범위는 순열을 모두 쓴 실행으로 적는다
- README 한계 절의 무작위 반례도 순열 20회 수치(`li-anode-phrase-all · topics · co_tagged`, +0.420 대 +0.148)였다. 순열 200회 기준 반례인 `li-anode-phrase · topics · co_tagged`(+0.262 대 +0.242, 순열 88회)로 바꿨다. "읽은 것" 절은 이미 이 값이었다
- `evaluate.rs` 모듈 주석이 "점수끼리의 비교는 `excess` 로 한다" 는 짝지은 검정 도입 전 권고를 담고 있었다. `excess` 는 크기, 우열은 `p_value` 로 고쳤다
- "귀무값이 0.5 가 아니다" 라는 결론은 바뀌지 않는다
